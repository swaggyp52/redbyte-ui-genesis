# RedByte Product Feedback Loop

The feedback loop preserves Connor's original product intent and prevents agents from turning a simple product complaint into an elaborate redesign.

It sits between raw feedback, Obsidian memory, Ollama synthesis, Codex execution, and the repo source of truth. The repo remains canonical; Obsidian is memory; generated reports are evidence candidates.

---

## Feedback Types

Use these categories when translating natural language feedback into a problem packet:

- workflow confusion
- visual/professionalism issue
- proof/trust issue
- overengineering issue
- product-definition drift
- stale docs/memory issue
- test/evidence gap
- scope creep
- classroom/lab overframing
- app behavior bug
- UX friction

Multiple types are allowed when the complaint crosses boundaries, but the packet must still name the smallest testable fix path.

---

## Product Interpretation Rules

- Always preserve the raw user wording exactly.
- Always map feedback to the product spine: Project -> Design -> Verify -> Map Pins / Hardware -> Export.
- Always distinguish symptom from root problem.
- Always check whether the issue is already known in repo docs, work queue, memory, or trace reports.
- Always identify the smallest testable fix.
- Always list what not to build.
- Always preserve a serious engineering tone.
- Do not convert every complaint into a broad redesign.
- Do not treat examples/labs as the product center.
- Do not hide behind docs if the app behavior is wrong.
- Do not let Obsidian memory override current repo truth.

---

## Problem Packet Schema

Every product problem packet must include:

- `id`
- `raw_feedback`
- `normalized_problem`
- `product_surface`
- `workflow_step`
- `problem_type`
- `severity`
- `evidence_sources`
- `related_claims`
- `related_docs`
- `likely_code_files`
- `related_tests_gates`
- `obsidian_memory_hits`
- `stale_memory_risks`
- `minimal_fix_options`
- `overengineering_risks`
- `do_not_build`
- `recommended_next_action`
- `definition_of_done`
- `codex_execution_prompt`

The packet is generated by `pnpm rb:problem:intake -- "raw feedback"`.

---

## Decision Rule

No implementation starts from ambiguous product feedback until a problem packet exists.

If the packet and work-driver disagree, report the disagreement. Do not force the task. Current repo truth, recent commits, and concrete tests/gates win over stale memory or generated reports.

---

## What This Protects

The loop protects the core RedByte product definition:

- RedByte is a proof-backed FPGA/digital-logic engineering workbench.
- The product spine is Project -> Design -> Verify -> Map Pins / Hardware -> Export.
- Verify is where behavior is proved.
- Map Pins binds design signals to Basys3 hardware; it does not replace proof.
- Export produces a Vivado-ready package with honest Draft vs Trusted status.
- Examples/labs are entry paths, not the center of the product.

This is not model fine-tuning. "Training the RedByte brain" means durable memory, reusable prompts, indexed context, traceable problem packets, and repo-backed execution.
