## 2. Current Product Thesis

RedByte V1 is a deterministic, browser-based Basys3 digital-logic lab workbench.

Its narrow promise:

- students build supported circuits visually
- students prove behavior in Verify with authored stimulus and Compare checks
- students map signals to real Basys3 resources
- students export a Vivado-ready package that matches current browser proof
- Vivado and physical hardware remain downstream proof tiers

RedByte is not a Vivado replacement, not a universal HDL IDE, not a broad FPGA platform, and not a SaaS classroom-management product.

- Verify's named testbench document owns its sequential execution intent. `overrideMode`, `runCycles`, `activeEdge`, `resetBehavior`, source/execution type, optional signal/reset identity, and `startLevel` persist with the browser-local scenario through save/reload, duplicate, rename, repair, and compatible Design changes. Pulse steps preserve rising, falling, high, and low behavior. The policy remains outside portable `RBProject`; runtime Verify, bring-up expectations, and generated `testbench.vhd` consume the same materialized execution vectors plus the resolved clock/schedule projection. Auto `runCycles`, automatic reset materialization, resolved clock data, starting level, and authored stimulus may therefore change derived package bytes, Export freshness, and old-receipt authority.
- Manual/custom sequential rows are settled authored samples. Only an authored low-to-high clock transition advances the supported rising-edge state model; repeated high, high-to-low, repeated low, and flat-low stimulus hold state. A falling transition is supported authored stimulus but is not falling-edge-triggered capture. Auto board-clock execution materializes cycle 0 and the selected run-cycle sequence; every Auto report row and generated VHDL assertion is post-rising-edge. An automatic reset sequence is part of those materialized rows—asserted in cycle 0 and deasserted later when applicable—not a hidden runtime reset prelude. Manual/custom execution injects no hidden reset.
- Basys3 mapping has one deterministic semantic projection: logical signal ID/label, direction, artifact port, board resource, package pin, I/O standard, exact XDC line, requirement, and conflict state. Map Pins, Export, generated artifacts, the embedded canonical manifest, and manifest-first Import use that projection. Semantic names such as `EN`, artifact names such as `SW`, board labels such as `SW0`, and package pins such as `V17` are related but not interchangeable count/identity domains.
- Export separates structural `blocked` / `downloadable`, `verificationTrust` `unverified` / `draft` / `trusted`, and action `not-downloaded` / `downloaded`. A receipt is current only for the exact package-source fingerprint, project/Verify hashes, current mapping, download kind, verification trust, and valid SHA-256 package hash. Download action alone never upgrades `verificationTrust`.
- Manifest-first Import restores `project.rbproj.json` before sibling transport files. The manifest is refreshed with the exact generated `top.vhd` and `top.xdc`. Canonical parser-expanded identities such as `SW[1]` and `LED[1]` may receive pins from embedded manifest XDC; malformed identities are rejected and loose sibling XDC cannot gain manifest authority. Supported RedByte-generated concurrent-assignment VHDL can reconstruct its generated graph; arbitrary behavioral HDL remains partial or blocked.

Map Pins groups Inputs, Outputs, and Clock / Reset and names every signal in a conflict. Export answers **What should I submit?** before detailed files while preserving course-specific submission policy.

Only a current Compare PASS with saved checks can support Export `verificationTrust: trusted`; Observe-only traces, a missing Compare, stale evidence, and failed checks retain their own repair routes. These evidence-currentness labels are not values of the Export `verificationTrust` enum.
