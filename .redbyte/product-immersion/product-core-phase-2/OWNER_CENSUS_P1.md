## Project Workspace (Project Center / control-center surface)

The Project workspace has ONE canonical persisted authority for project state: the zustand store `useProjectRuntime` in projectRuntime.ts (persisted via `persist`, wrapped by the `projectRepository` facade for save/autosave/recovery). It owns identity, circuit, hierarchy, IO rows, hardware mapping, scenarios, vectors, the verify run ledger, and health. HOWEVER the ACTIVE TOP MODULE and board/part are NOT in that store — they live in a SECOND, ephemeral authority: `fpgaConfig` React useState in IdeApp.tsx (line 387), derived from projectName via `buildIdeFpgaConfig`/`buildTopEntityName`, editable only through the Technical-details inputs, and reset (not persisted) on reload. There is NO `setActiveTop` and no `top` field in the store; `effectiveTopEntityName = normalizeTopEntityName(fpgaConfig.top, buildTopEntityName(projectName))`. ProjectSurface.tsx renders a rich Project explorer (Design Sources, Reusable Components, Simulation Sources, Constraints, Recovery) but those rows are DESCRIPTIVE/NAVIGATIONAL only — they route to other surfaces (onOpenDesign/onOpenVerify/onOpenHardware); the only in-place actionable controls are rename, Save now, Restore last save, Duplicate, Reset, Change-Project entry paths, and the top/part text inputs. Real commands already exist: setProjectIdentity (identity), handleRenameProject, handleDuplicateProject/handleSaveAsProject, handleSaveProject, handleRecoverProject, all wired through the `commandRegistry`/`IDE_COMMAND_IDS` seam. Sources/filesets, constraint sets, and the run ledger (`verifyRunHistory`, 50-entry ring) are all held in the runtime but NOT surfaced as operable documents in Project — they appear only as counts/derived compile-order text. To make Project an operational control center, new features must extend `useProjectRuntime` + its actions and the command registry, and the `fpgaConfig` second authority must be folded into the store (add a real top/board/part slice + setActiveTop) rather than kept as component state.

## Ephemeral live experiment state (Manual Bench live-drive + Virtual Basys3 Board) over one CircuitEngine

ONE ephemeral experiment state exists, not two: the zustand slice `state.sim` (RuntimeSimState) in projectRuntime.ts owns all live drive values (`sim.inputs`) and all computed signals/outputs (`sim.signals`, plus `tick/trace/running/probes`). Every interactive live control already writes this one slice through the store actions `actions.sim.setInput` / `toggleInput` and reads back `sim.signals`. The DesignSurface on-canvas INPUT/Switch toggles and inspector toggle drive it via the `onRuntimeSimSetInput` prop (= `setRuntimeSimInput` = `actions.sim.setInput`) and read via `liveSignals` (derived from `runtimeSim.signals`). The HardwareSurface Virtual Board drives/reads the SAME slice through the `useIoBus` hook (ioBus.ts): switches call `ioBus.actions.toggleSwitch`→`setInput`(=`onSimSetInput`=`actions.sim.setInput`); LEDs read `sim.signals`/`sim.inputs` via `readBit`. So Bench and Virtual Board are already two views over one store in both directions — the wiring is correct today. The canonical evaluator is the module-singleton `runtimeSimEngine` (a `CircuitEngine` from @redbyte/rb-logic-core) in sim/simEngineCore.ts, invoked through simEngine.ts's `advanceSimulationStateFromModel` / `recomputeSimulationStateFromModel` / `resetSimulationStateFromModel`; every setInput/toggle/step/reset recomputes through it, so there is exactly one evaluator. The real gaps are: (1) there is NO live-drive "Manual Bench" surface in Simulate/Verify at all — VerifySurface is scenario/vector (persistent) authority, not ephemeral live drive, so if a Manual Bench is wanted in Simulate it must be built as another consumer of `actions.sim.setInput/toggleInput` + `runtimeSim.signals`, never a new store; (2) `actions.sim.toggleInput` is defined but unwired to any UI (both existing controls use `setInput`, ioBus re-implements toggle by read+setInput); (3) Virtual Board buttons are momentary via `setButton`→`setInput` with no dedicated pulse action.

## Board & Constraints / Pin Planner (Basys3 mapping authority)

The single writable mapping authority is the zustand slice `hardwareMappingV2: HardwareMappingDocumentV2` in projectRuntime.ts, mutated ONLY through four store actions (setMappingPin, setMappingPins, applyHardwareMappingEdit, autoSuggestMapping); every one routes through deriveAuthoritativeHardwareState so the flat `projectIoRows` and the export `mappingProjection` are pure DERIVED read-models — never write them. Structured edits are a pure reducer (applyHardwareMappingV2Edit) over a 5-op union. Board electrical facts live in basys3Pins.ts as BASYS3_BOARD_PROFILE; conflict classification and the exact XDC line per port are computed downstream in basys3ExportContract.ts (Basys3SemanticMappingProjection.conflictState + exactXdcLine), and the constraint file is assembled by buildTopXdc in basys3Bundle.ts. Actionable today: per-pin assignment, structured bus/slice/group entries, Base[N] bulk bus mapping (SW/LD families only), naive sequential auto-suggest, conflict DETECTION with visual flags, deterministic XDC generation. Descriptive-only: I/O bank / VCCO voltage / drive / slew / differential metadata (differentialRelationship field exists but is ALWAYS null); IOSTANDARD is hard-locked to LVCMOS33. There is no conflict-repair action (only navigate-to-next-issue), no single editable assignment grid, and no XDC diff — generated XDC is preview text only. Two parallel bus paths (flat Base[N] planner via setMappingPin vs structured V2 bus entries via applyHardwareMappingEdit) can diverge.

## Build & Export / package generation (RedByte IDE)

The export subsystem has ONE canonical package generator: buildExportViewModel() in viewmodels/buildExportViewModel.ts (~line 197). It is a pure function that takes (project, verifyLastRun, activeScenario) and returns the complete ExportViewModel — artifacts[], pinTable, mappingProjection, diagnostics, exportHash, topAuthority, and exportedScenario provenance. It orchestrates exportProjectAsBasys3() (basys3ExportService.ts:335 — the explicitly-declared ONLY Basys3 bundle generator), hierarchical VHDL, a runtime-backed testbench (behind an authority firewall), bring-up artifacts, and deterministic provenance headers stamped into every text artifact (buildProvenanceHeader, ~line 1305). The workbench "location" is split across THREE non-unified owners: (1) which mode — `currentMode`/`activeMode` is React `useState` local to `IdeApp` (IdeApp.tsx:276-277), the ONLY thing pushed to browser history/URL; (2) which module — `hierarchy.activeModuleId`, a single string in the projectRuntime zustand store, mutated only through the `setActiveModule` action; (3) which nodes/wires + camera — a SEPARATE zustand store `useLogicViewStore` (`selection:{nodes,wires}`, `camera`). ## Census Persistence + Project Format + Recovery (working-state save/reload)

There are THREE distinct localStorage writers (no IndexedDB anywhere), and only two of them are canonical state owners. (1) The zustand `persist` middleware on `useProjectRuntime` (key `rb.ide.project-runtime.v1`, envelope version 5) is the authoritative autosave of the entire in-memory design/session store: it persists project identity, circuit, hierarchy (including `activeModuleId`), hardwareMappingV2, projectIoRows, projectVectors, scenarios (+steps/probes/sequentialPolicy), activeScenarioId, customVectors, design undo/redo stacks, designRevision, verify ledger, sim state, projectHealthCore, macros, and customComponents — see `partialize` at projectRuntime.ts:2479 and rehydration via `mergePersistedRuntimeState` at :2527.
