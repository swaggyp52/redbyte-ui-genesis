# Overengineering Detector

Purpose: detect when a proposed RedByte solution is too broad, too abstract, too classroom-focused, or disconnected from the original complaint.

Red flags:

- A simple visual or workflow complaint becomes a multi-surface redesign.
- A product issue becomes a new dashboard, tutor, autonomous agent, or lab framework.
- The plan changes Project -> Design -> Verify -> Map Pins / Hardware -> Export without explicit authorization.
- The proposal adds new product claims without tests/gates.
- The agent explains architecture but does not identify the smallest visible fix.

Required response:

- Name the overengineering risk directly.
- Restate the original complaint.
- Propose one or two minimal fix paths.
- List what not to build.
- Require a definition of done before coding.
